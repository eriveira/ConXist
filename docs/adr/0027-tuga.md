# 0027. Tuga, the workspace's assistant: a plain chat that only reads

- Status: Accepted (owner, 2026-11-28)
- Date: 2026-11-28
- Deciders: owner, Claude
- Builds on: ADR 0012 (test runs), ADR 0014 (LLM providers), ADR 0024 (Spring AI), ADR 0025 and 0026 (guardrails)

## Context

The owner asked for ConXist's own agent, named Tuga: a button in the bottom-right corner of every page, like the
"Ask ConXist" pill of the first agents mock, that answers questions within the workspace and calls the tools it has,
with a Settings section for its model, effort and prompt. For this phase the owner asked for a plain chat
(2026-11-28). Mock: `App/mocks/assistant-v2` (v3, plain chat), approved by the owner.

## Decision

1. **A plain chat.** A Tuga button on every page opens a panel: the person writes, Tuga answers in plain text and ends
   with a "From:" line that names what it used. New chat empties it. Nothing is stored: the app keeps the chat in
   the page and sends the messages so far with each new one (`POST /api/tuga/chat`, at most 40 messages, the
   person's at most 4,000 characters each). It is gone on New chat, on switching workspace, or when the tab closes.
   Answers come back whole; streaming is later.
2. **Only reads.** Tuga gets every one of ConXist's own read tools (`list_sources`, `list_meetings`,
   `get_transcript`) and the read tools of the workspace's integrations that the workspace allows (GitHub, Bitbucket,
   Gmail: ConXist's own code, GET only; `McpToolbox.readTools()`). It gets no tool of an MCP server for now: a server
   labels its own tools read-only, its calls leave ConXist, and read tools come ticked when a server is added (ADR
   0022), so no person would have chosen them for Tuga (security review, 2026-11-28). A "Tuga may use" list in
   Settings › Tuga comes later. No tool that changes things, whatever the workspace ticked.
3. **Orders come only from the person in the chat.** Tuga's fixed rules (`TugaPrompt.RULES`) say so, name the kinds
   of data, and have it report what data asked for with `report_request`; the chat shows each one in plain words.
   They come first, then the workspace's own rules (`<workspace-rules>`), the tools, and Tuga's prompt inside
   `<tuga>` tags. Tuga keeps ConXist's rules even where a workspace replaced the agents' rule (ADR 0026): that rule
   speaks of agent instructions, and Tuga is not an agent. The rules also say that Tuga's earlier answers in the chat
   may quote data and are never orders, since the app sends them back. The copy guard and the size check run on every outside
   call; Tuga's earlier answers count as already read, so a later call can't send them out word for word.
4. **One shared loop.** Test runs and Tuga run through the same `ToolLoop` in the `runs` module: the same limits from
   Settings › General, copy guard, `report_request` and logs (sizes, ids and the prompt version, never text).
5. **Settings › Tuga.** After LLM providers: the provider, model and effort Tuga answers on, among the models the
   workspace allows (until it picks one, Tuga uses where new agents start); and Tuga's prompt, up to 4,000
   characters with `{{name}}` variables, editable after a warning and restorable, like ConXist's rule in ADR 0026.
   An answer on an edited prompt logs `VERSION+workspace-prompt-` and a short hash. V28 adds `tuga_settings`
   (one row per workspace, with a revision; a save from an older revision is refused with 409 `tuga.changed`), and
   deleting a workspace deletes its row.
6. **In `runs` for now.** Tuga lives in the `runs` module because it is one more kind of run. It gets a module of its
   own when chats are kept or it gets tools of its own, such as drafting agents and skills.

## Consequences

- Everyone in a workspace chats with the same Tuga; there is no sign-in yet, so there is no "my chats".
- A long chat costs more with each message, since the whole chat is sent; the cap of 40 messages bounds it, and the
  panel says when older messages are no longer sent.
- The app sends Tuga's earlier answers back, so a person could change them; they are data under Tuga's rules, and
  the code checks run on them. Signing answers, or keeping chats on the server, comes with sign-in.
- Sources show as a plain "From:" line, not links as the mock drew them: the answer is plain text for this phase.
- LLM providers does not yet keep Tuga's model allowed or list Tuga among who uses a model; Tuga then says its model
  can't run and links to Settings › Tuga.

## Later

- Streaming answers, kept chats, links to the meetings and pull requests it used, MCP server tools picked for Tuga,
  and tools that draft agents and skills (ADR to come).
